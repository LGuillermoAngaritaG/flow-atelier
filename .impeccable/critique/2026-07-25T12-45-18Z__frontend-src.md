## Overall Impression

The craft is real and the visual system is coherent. What holds it back isn't taste — it's that the Dashboard, the landing route and the one carrying the product's core action, is the least finished of the three surfaces. The Designer is excellent. The Kanban is solid. The Dashboard buries its primary button below the fold behind a scroll trap, is the only route that doesn't adapt to viewport, and leaks a JSON parser exception the moment the backend isn't there.

Biggest opportunity: treat the Dashboard as unfinished and bring it up to the standard the Designer already sets.

## What's Working

1. **The color system is genuinely engineered, not decorated.** Every token is OKLCH with theme-specific lightness chosen to clear 4.5:1, and the comments say why (`L 0.48, not 0.62: at 0.62 every piece of text-primary landed at 3.64:1`). Measured: muted-foreground 7.82:1 dark / 8.12:1 light, primary 9.44 / 6.58, tool colors 5.68–10.35. A full-page audit of every rendered text node found **zero** failures in dark and **four** in light — all placeholders, the one thing no one set explicitly.

2. **Accessibility was treated as structure, not a checklist.** Global `:focus-visible` ring, a named z-index scale instead of `9999`, `prefers-reduced-motion` collapsing every animation, `KeyboardSensor` on the kanban drag context, Radix primitives rather than hand-rolled dropdowns (with a comment explaining exactly why the hand-rolled one was replaced), status communicated by dot *plus* text rather than color alone.

3. **Empty states teach.** `"Nothing running. Drag a task here, or press run on its card, to start it."` instead of "— empty —". The comment says the change was deliberate.

## Priority Issues

### [P1] The primary action is below the fold, behind a scroll trap

On `/dashboard` at 1234px, `▸ run conduit` sits roughly 1100px down. Worse, the conduit picker is a 320px inner scroll region sitting in the middle of the page: six wheel ticks with the cursor over it moved the page **zero pixels**. A user scrolling toward the run button gets their input captured by the list.

**Why it matters**: This is the product's core action on its landing route. The first thing a new user does is scroll, and the page appears not to respond.

**Fix**: Let the page scroll — drop `ScrollArea` from the picker and cap it by row count instead, or pin the run/schedule actions to the bottom of the form column.

**Suggested command**: `/impeccable layout`

### [P1] The Dashboard is the only route that doesn't adapt

Three separate measurements:

- The two-column grid is gated on `xl:` (1280px). Measured `innerWidth` 1234 → single column, so "recent flows" — the panel that tells you whether the run you just started worked — is a full screen below the run button. The container is capped at `max-w-[1280px]`, so at `lg` each column would still be ~480px. The whole 1024–1280 band gets the stacked layout for no reason.
- `Dashboard.tsx:102` is `px-10 py-10` with no breakpoint (measured 40px). Kanban is `px-4 py-6 lg:px-10 lg:py-10`; Designer is fluid. Dashboard is the outlier.
- `input-form.tsx:97,127` use `grid-cols-[140px_1fr]` with a 24px gap, unconditionally.

At 390px those compound: 80px padding + 140px label + 24px gap leaves **146px** for every input, including a working-directory path field.

**Fix**: `lg:grid-cols-[...]` for the page grid, `px-4 py-6 lg:px-10 lg:py-10` for the section, and stack label-above-input below `sm` in the two `grid-cols-[140px_1fr]` rows (`ProjectSelector.tsx:18` and `FieldRow.tsx:8` have the same pattern).

**Suggested command**: `/impeccable adapt`

### [P1] Raw exceptions reach the user, twice, and neither names the cause

With the API unreachable, `/dashboard` renders:

> **FAILED TO LOAD CONDUITS**
> Unexpected token '<', "<!doctype "... is not valid JSON

…plus a separate `Failed to load schedules` toast for the same root cause, while the header simultaneously reads **0 CONDUITS** — asserting a count it doesn't have.

**Why it matters**: Three signals, one cause, and the most prominent one is a JavaScript parser internal. The actual diagnosis ("the API server isn't running") appears nowhere. The `0 CONDUITS` is worse than unhelpful — it's false.

**Fix**: Map fetch/parse failures to one cause-level message naming the origin it tried (`BASE_URL` is already derived at runtime). Put the raw text behind a details toggle. Render `—` instead of `0` when the count is unknown. Suppress the schedules toast when the conduits fetch has already failed.

**Suggested command**: `/impeccable harden`

### [P1] Placeholders are the one untuned color — and they carry the hints

No `::placeholder` color is set anywhere, so Chrome's default applies: 50% alpha of the input's own `color`. Measured `oklab(0.94 … / 0.5)` → **3.29:1 in light** (fails AA) and **4.63:1 in dark** (passes, but by accident of where the default landed).

This matters more than usual because in `input-form.tsx:147` the placeholder *is* the field's hint: `placeholder={hintStr(hint)}`. It's content, not decoration.

**Fix**: `placeholder:text-muted-foreground` on the input classes — that token already measures 8.12:1 light / 7.82:1 dark. Every other color in this system was deliberately chosen; this one was left to the browser.

**Suggested command**: `/impeccable polish`

### [P2] Two hit-target standards, two icon vocabularies, and structure drawn in invisible lines

Three consistency failures that share a root: the design system was applied to hand-rolled elements but not to the shared primitives.

- **Hit targets**: 8 of 15 buttons on `/dashboard` measure under 44px. The primary `▸ run conduit` is **32×132**. Meanwhile every hand-rolled control is `h-11` (44px) — nav links, menu items, inputs, the mobile tools tab. All 39 `<Button>` uses are `h-8`/`h-9`. The app set itself a 44px standard and its own button component doesn't meet it.
- **Icons**: lucide-react (`Menu`, `Undo2`, `Redo2`) alongside typographic glyphs (`▸ ◷ ⠿ ×`) at 8 sites. The glyphs sit *inside* accessible names — `▸ run conduit` is announced as "black right-pointing small triangle, run conduit".
- **Borders**: measured **1.53:1** (dark) and **1.47:1** (light); `border-border/50` and `/60`, used at 43 sites, drop to **1.26:1** and **1.19:1**. WCAG 1.4.11 asks 3:1 for the visual information that identifies a component. 26 inputs use a bottom border as their *only* affordance — there's no fill, no box, just that line.

**Fix**: raise `Button`'s `sm`/`default` to `h-9`/`h-11`; replace glyphs with lucide equivalents (`Play`, `Clock`, `GripVertical`, `X`) marked `aria-hidden`, or wrap them in `<span aria-hidden>`; add a `--color-border-strong` at ~3:1 for input underlines and control outlines, keeping the current hairline for decorative dividers.

**Suggested command**: `/impeccable polish`

## Persona Red Flags

**Alex (Power User)**: Undo/redo are the only keyboard shortcuts in the product, and they exist only in the Designer. There is no shortcut to run a conduit — the core action — no route switching, no command palette. Alex's path to the primary button is: scroll (fails, list eats the wheel), move the cursor off the list, scroll again, then hit a 32px target. No bulk actions anywhere: can't run two conduits, can't multi-delete schedules, can't multi-select kanban cards.

**Sam (Screen reader / low vision)**: Real strengths here — the global focus ring, Radix primitives, `KeyboardSensor` for drag, genuine `<label for>` associations, status as dot-plus-text. Then: text inputs whose only boundary measures 1.26–1.53:1, so at rest a low-vision user can't see where the field is (the focus ring is fine — it's the resting state that's invisible); placeholders at 3.29:1 in light; 30 sites at 9px and 40 at 10px, where contrast passes but stroke weight doesn't; and `▸`/`◷`/`⠿` announced as glyph names inside button labels.

**Riley (Stress tester)**: Broke it in the first thirty seconds without trying — starting the frontend without the backend produced a JSON parser exception rendered as the error body, a redundant toast, and a header count of `0` that was simply untrue. Riley would also note `proj-${Date.now()}` as a project ID collides for two projects created in the same millisecond.

## Minor Observations

- **The 52px serif page title costs 22% of the fold** on both `/dashboard` and `/kanban` to say something the active nav item already says. "Run a conduit" above a nav reading DASHBOARD.
- **`SELECTED` replaces the task count** on the selected conduit row — you lose the count exactly when you're deciding whether to run it.
- **Kanban's most prominent toolbar control is DELETE PROJECT**, top-right at full weight, while the primary "+ ADD" is 12px inside a column header. Destructive outranks primary.
- **Designer edge labels collide with nodes** — `MATCH` renders clipped to `ATC` behind the `smoke_tests` node.
- **17 sites apply opacity on top of tokens** (`text-muted-foreground/60` and friends) that were deliberately tuned for contrast. Dark measures 5.09:1 so it passes today, but the pattern defeats the tuning by design.
- **The Designer minimap** occupies ~220×160px of canvas showing barely-distinguishable gray blocks.
- **Type floor**: 70 uses of 9px/10px. Defensible in a dense tool, but 9px for task type labels and tool names is below where stroke weight holds up regardless of contrast ratio.
- **No help affordance exists anywhere in the app.** "Conduit" is invented vocabulary with no inline definition. The empty state reads "create one in the designer to get started" and is not a link.

## Questions to Consider

- The Designer is clearly the surface you cared most about. What would the Dashboard look like if you gave it the same attention — is it even the right landing route, or should `/` go to Kanban?
- If "conduit" is the product's central noun, where does a new user learn what one is? Right now the answer is the README, outside the app.
- The 52px serif titles are the strongest brand gesture in the product and they sit on the two routes where vertical space is scarcest. Would the brand survive moving that voice into the top bar and giving the fold back to the task?
- Every hand-rolled control is 44px and every shared `<Button>` is 32px. Which one is the standard?
